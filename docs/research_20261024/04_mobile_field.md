# 手机端外业 GIS：场景、参照与技术边界

证据状态：本文是方向性研究。QField、Mergin Maps Input、ODK/Kobo、Field Maps/Survey123 的总体形态来自公开资料与领域常识，本轮没有逐仓库核对许可证和最新版本；移动浏览器能力会随系统版本变化，正式设计前需在目标机型实测。所有“不能做”的建议都应按实测结果调整，而不是当成永久结论。

## 1. 手机端为什么值得做

手机的价值不是把桌面 GIS 缩小，而是把 GIS 带到现场：人、位置、照片、语音、时间和判断在现场同时发生。外业人员真正高频的动作是找到某个地块或核查点、确认它是否与图上一致、记录现状和问题、拍照、留下轨迹、回到办公室后让数据进入分析和报告。手机不适合做阻力面、InVEST、批量栅格或复杂制图，但它可以决定一次分析是否可信。

TIPHYS 的手机端应该定位为“外业核查与采集终端”，而不是“手机版 ArcGIS”。它与桌面/浏览器共用同一套图层、任务和成果，但在交互上只保留现场最需要的能力。

## 2. 开源与商业参照的逻辑

QField 与 Mergin Maps Input 是开源外业 GIS 的代表，较有把握的共同逻辑是：把 QGIS 工程打包成离线项目，手机上携带图层、底图、表单和编辑规则，现场采集后同步回项目；同时记录定位精度、照片附件和修改历史。它们的优势是离线能力、与 QGIS 的工程兼容和外业表单；弱点是学习成本、工程准备依赖桌面、复杂同步需要服务端。具体许可证、同步服务条款与当前版本能力需核实。

ODK Collect 与 KoboToolbox 更偏表单采集：强项是结构化问卷、跳过逻辑、离线提交和数据汇总，地图与空间分析较弱。它们说明“表单 + 离线 + 审核”是外业数字化的核心，而不是三维渲染。

Esri 的 Field Maps、Survey123、QuickCapture 则把外业采集与 ArcGIS 平台、任务分派、附件和门户同步结合，强项是组织级管理与生态整合；这类产品的具体功能和授权方式需核实。它们对 TIPHYS 的启示是：任务、表单、定位质量、照片、同步和审核必须是一条链，单独做一个“能打点的地图页”没有长期价值。

## 3. 移动 Web 能做什么，不能承诺什么

| 能力 | 现实边界 | 产品决策 |
|---|---|---|
| 定位 | 浏览器 Geolocation 需要 HTTPS，通常在前台运行；后台连续定位不可靠 | 外业记录以单次定位和前台轨迹为主；后台轨迹不承诺 |
| 精度信息 | 浏览器可返回精度半径，但不等于测绘级精度 | 记录 accuracy、设备和时间；高精度需求另评估外接设备 |
| 相机与照片 | 可通过文件选择或 getUserMedia 获取照片，需处理压缩、方向和隐私 | 照片作为附件，保留拍摄时间、位置和任务关联 |
| 语音 | Web Speech/录音能力依浏览器与系统而异，中文识别质量需实测 | 语音转文字作为辅助输入，必须让用户确认结构化结果 |
| 离线 | PWA/Service Worker 可缓存页面与数据；IndexedDB/OPFS 可存较大数据 | 支持离线任务包；明确存储配额与清理策略 |
| 后台同步 | 系统可能暂停后台任务，iOS 限制更多 | 以回到前台后同步为主，不承诺“随时自动上传” |
| 蓝牙/GNSS | iOS Safari 不支持 Web Bluetooth；NTRIP 需要 TCP/串口链路 | 不在手机 Web 承诺 RTK/NTRIP；未来评估原生壳或外接设备方案 |
| 大栅格/WASM | 手机内存与 WASM 地址空间有限，24 MB 级 WASM 与高分辨率栅格风险高 | 手机只看结果与核查点，不在端上跑廊道、InVEST、批量栅格 |
| 分享与协作 | 链接分享容易，权限与冲突处理难 | 采用任务与记录级权限，避免直接把整个工程公开 |

这些边界意味着手机端的 AI 也不应依赖大模型在端上跑重分析。更现实的方式是：表单校验、任务导航、异常提示和结构化记录在本地完成；需要模型时，用户在联网且授权的情况下调用，模型只做解释、归纳和建议，不替代现场确认。

## 4. 手机端 P0 功能

第一是任务收件箱。用户打开手机就能看到分配给自己或本设备的外业任务，包含任务目的、目标图层、核查点、截止时间、表单和离线包状态。任务来自桌面/浏览器中的分析结果，不需要在现场重新找数据。

第二是离线任务包。一个包至少包含任务元数据、表单 schema、目标要素或核查点、可离线底图/瓦片、必要的参考图层和规则。下载时显示大小、范围和更新时间；进入现场后无网络也能打开。

第三是现场采集。支持点、短轨迹和必要的小范围面，支持拍照、录音/语音备注、手写或表单字段、定位精度记录、时间戳和设备信息。字段校验在本地执行：必填、数值范围、枚举、重复点、离目标点距离、照片数量。采集结果先写入本地队列，不允许因为网络失败丢失。

第四是导航与核查。用户可以从任务列表直接导航到目标点或下一个核查点，看到目标与本地的关系，记录“符合/不符合/无法判断”，并附照片和说明。地图要清楚显示离线状态、定位精度和同步状态，不用专业术语掩盖不确定性。

第五是回传与审核。网络恢复后按队列同步，显示每条记录的状态；冲突不能静默覆盖。办公室端看到的是带位置、时间、精度、照片和表单的记录，能逐条接受、退回或标记异常，并把结果并入分析图层。

第六是 AI 辅助，但要有边界。语音可以转成结构化备注，模型可以根据照片/文字提示可能的异常和缺失字段，Agent 可以汇总“今天哪些点最值得复核”。任何自动判断都要标明置信度和依据，最终由人确认；没有联网或未配置模型时，界面明确降级为规则校验。

## 5. 最小外业闭环

以生态廊道为例。桌面完成廊道和优先级分析后，系统把“最不稳定或最需要修复的 20 个路段/节点”生成外业任务，附带目标位置、为什么选它、需要核查的表单（土地利用现状、障碍类型、通达性、照片）和离线底图。手机下载任务包后离线采集，记录实际位置、照片、语音和判断。回到有网络的环境后同步，桌面端把记录与原廊道结果关联，更新核查状态，Agent 汇总“哪些优先级结论被现场支持、哪些需要调整阻力权重”，并生成新的图件和报告。

这条闭环需要三个新数据结构：外业任务、外业记录和同步事件。外业任务关联源分析、目标要素、表单和离线包；外业记录关联任务、目标要素、实际几何、精度、表单、媒体和校验结果；同步事件记录每次上传、冲突、接受和退回。原始分析图层不被现场记录直接覆盖，现场修改作为新版本或新记录进入审核流程。

## 6. 手机端明确不做

不做完整图层编辑与拓扑编辑，不做阻力面、廊道、InVEST、批处理和大栅格 WASM，不做复杂符号化与版面出图，不承诺后台连续轨迹和高精度 RTK，不做需要多人实时协同的复杂冲突合并。手机端只做“到达现场、记录事实、完成核查、安全回传”，把重分析和成果制作留给桌面/浏览器。

## 7. 设计原则与验收

手机界面应单手可操作，按钮和字段要大，地图与任务状态优先，减少层级；离线、定位中、精度不足、待同步、冲突和退回等状态必须显眼。验收时至少覆盖：飞行模式下完成一次任务包下载后的采集；无网络关闭页面后重新打开不丢记录；恢复网络后按顺序同步；重复提交与几何/属性冲突不静默覆盖；定位精度低时提示并记录；照片与记录关联正确；办公室端能追溯到源任务和分析版本。

只有这些基础通过，才值得增加更聪明的现场 AI。否则，一个会说话但会丢数据的手机端，比没有手机端更伤害信任。
