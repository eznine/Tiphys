# AI+GIS 同类产品研究（方向性）

证据状态：本轮外部检索在开始后中止，以下内容是依据项目已有调研文档、公开产品形态和通用架构知识整理的方向性判断，没有逐条引用最新官方文档。凡涉及具体商业产品当前功能、价格或版本的地方，均标为待核实，不能作为对外宣传依据。正式使用前按 `06_evidence_and_verification.md` 的清单复核。

## 1. 四种主要形态

当前“AI+GIS”产品大致分成四类，不是所有产品都真的在同一层面竞争。

| 形态 | 代表逻辑 | 强项 | 普遍缺口 |
|---|---|---|---|
| 自主 GIS / 代码生成型 | 用户说目标，LLM 生成 Python/ArcPy/GeoPandas 脚本并运行 | 能覆盖长尾任务，看起来“什么都能做” | 结果难复现、依赖环境、坐标和单位错误不易发现、失败后难恢复、安全边界弱 |
| 固定工具 Agent | 把 GIS 工具注册成函数，LLM 负责选工具、填参数、串联 | 确定性计算稳定，适合生产 | 工具覆盖有限；跨引擎状态容易割裂；Agent 看不到另一套引擎的图层 |
| 云数据平台 Agent | 自然语言转 SQL/云工作流，分析仓库里的空间表 | 数据就在计算端，治理与协作强 | 依赖上云；本地文件、桌面数据、外业采集弱；复杂 GIS 格式与制图能力有限 |
| 协作地图 / AI 制图平台 | 对话生成地图、样式、洞察并分享 | 上手快、可视化与协作好 | 深度空间分析、数据质检、投影与专业模型不是重点 |

这四类产品共同做对的事情是：把自然语言限制在“计划与选择”，把实际计算交给确定性工具或数据库；都会保留某种形式的图层/项目上下文；都开始加入人工确认和操作记录。共同没解决好的事情是：**跨引擎的数据与任务状态、结果验证、专业数据质量、从分析到外业再回到分析的闭环。**

## 2. 具体产品的公开逻辑与判断

以下判断的置信度分为“较有把握”和“待核实”。没有写“源码核对”的，都不是本轮实际读到的源码。

Esri 的路线较有把握的部分是把 AI 助手嵌入 ArcGIS Pro/Online 的既有工程与地理处理体系，让自然语言去调用已有工具、数据和地图上下文。其优势是工具、数据、制图与协作体系完整，而不是模型本身。需要核实的是当前版本具体支持哪些自然语言操作、是否能跨工程维持上下文、结果如何验证。对 TIPHYS 的启示是：不要和 Esri 比工具总量，要对齐“工程上下文 + 固定工具 + 结果可追溯”，并在跨引擎和解释层做差异。

CARTO 一类云原生平台较有把握的逻辑是把自然语言分析落在云数据仓库上，利用 SQL 与空间函数执行，优势是数据不动、治理清晰。对 TIPHYS 的启示是：数据位置决定执行引擎，这个原则同样适用于本地 WASM/Python；但 TIPHYS 的差异应放在本地文件、桌面双引擎和手机外业，而不是复制云数仓。

Felt 一类协作地图平台较有把握的逻辑是地图协作、分享和低门槛编辑，AI 用来加速制图、标注或简单分析。Atlas、Aino 等 AI 地图产品普遍强调从提示快速生成地图或空间洞察，但公开材料通常不展示完整的坐标校验、专业分析验证和本地数据闭环。这些产品说明“生成得快、好看、能分享”有市场，但不能证明它们能可靠完成生态廊道、遥感时序或测量质量检查。具体能力待核实。

开源自主 GIS 研究（让 LLM 生成代码、调用 GIS 库或工具）较有把握的共同点是：用基准任务证明“能完成”，但很少处理真实项目中的坐标未知、数据脏、长任务中断、结果复现和权限。TIPHYS 不应把“生成代码”作为默认路径，而应把 LLM 放在工具选择、参数解释、错误恢复和结果解读上。

## 3. 哪些地方应当与别人一样

必须对齐成熟产品的四个基础。第一是工程上下文：图层、坐标系、选择集、研究区、任务历史要能被 Agent 稳定读取，而不是每次从聊天里猜。第二是确定性工具：缓冲、裁剪、投影、融合、分区统计等由可信实现执行，LLM 不直接算几何。第三是人工确认与可追溯：破坏性操作、导出、远程上传和覆盖必须确认，结果要有参数与来源。第四是熟悉的 GIS 工作台：图层树、属性表、符号化、右键菜单、出图，用户不需要为了用 AI 重新学习 GIS。

这些是入场券，不是差异化。缺少它们，产品会被认为“演示很惊艳，干活不可靠”。

## 4. 可以做得更好的地方

第一是**统一多引擎**。多数产品只有一条执行路径；TIPHYS 桌面同时具备 WebView WASM 与 Python，浏览器具备 WASM，未来还可接远程 GEE。真正有价值的是让 Agent 只理解一套能力，由调度器根据数据位置、规模、精度和引擎能力选择执行，并把两套引擎的图层与任务统一。这个优势来自架构，不是模型。

第二是**验证优先**。行业里普遍把“工具返回成功”当成“任务完成”。TIPHYS 可以把 CRS、单位、几何有效性、要素数、范围、NoData、容差、双引擎对照和敏感性检查做成产品的一部分。对生态、环境、测绘用户，这比多 100 个算法更有价值。

第三是**分析到外业的闭环**。协作地图产品强在分享，桌面 GIS 强在分析，外业产品强在采集，但三者通常分离。TIPHYS 可以把分析结果直接变成离线外业任务，回传后再更新分析和报告。这是手机端存在的真正理由，也是很难被通用聊天产品复制的部分。

第四是**领域工作流而非工具堆**。生态廊道、生境质量、遥感时序、测量数据质检等场景有明确的数据要求和验收标准。把一条流程做对、做可解释、可复现，比接入一千个没有上下文的算法更能建立信任。

第五是**本地优先与透明边界**。本地数据默认留在本地，模型密钥由用户控制，跨引擎转换和远程执行明确说明数据去向。对于政府和科研用户，这往往比“全自动云端”更重要。

## 5. 不应该做的差异化

不建议把“自然语言生成任意 GIS 代码”作为卖点。它会把可靠性、依赖、安全和复现问题转嫁给用户，也削弱 TIPHYS 已经积累的固定工具与任务机制。不建议做“万能聊天框 + 一堆按钮”，因为用户真正缺的是任务完成，不是更多入口。不建议在 GEE、InVEST 或生态模型尚未验证时宣称“已支持”，这类能力一旦结果不可信，会破坏整个产品的专业信誉。

## 6. 对 TIPHYS 的定位结论

TIPHYS 的合理定位是：**面向生态、环境与测绘任务的本地优先 AI+GIS 工作台，能把自然语言任务可靠地执行成有验证、有血缘、可交付、可外业核查的空间成果。**

与通用 AI 地图产品相比，优势是专业分析、桌面双引擎和验证；与 ArcGIS/QGIS 相比，优势是任务编排、自然语言、解释与跨端闭环；与自主代码生成 Agent 相比，优势是确定性、可复现和安全边界。这个定位不要求工具数量最多，但要求每一条主推工作流真的能交付。
